# План: Универсальные профили — шаги с проверками

> Архивный план реализации. Код профилей уже находится в линии `0.3.x`;
> актуальная эксплуатация описана в корневом `README.md`. Пункты живой
> публикации не дают разрешения менять production.

Спека: `2026-07-04-universal-business-profiles.md`. Каждый шаг ≤ ~1 час, кончается
проверяемым состоянием. Ветка: `feature/business-profiles` в avito-bridge (не main!).

## Этап A — фундамент (без ключей 2-го аккаунта, кондиционеры не трогаем)

1. **Снапшот-тест кондиционерного фида.** Зафиксировать текущий XML на живых данных
   (или фикстуре) как golden-файл.
   Done: тест `test_feed_snapshot.py` зелёный; любое расхождение XML ловится.
2. **`BusinessProfile` + загрузка `profiles/*.yaml`.** Текущий config.yaml становится
   `profiles/conditioners.yaml` (или загружается как профиль по умолчанию — без
   перемещения файла, обратная совместимость).
   Done: `load_profile("conditioners")` возвращает те же значения, что `load_config()`;
   снапшот-тест фида зелёный.
3. **Интерфейс `Source` + рефактор oasis_db под него.** `fetch_raw_products()` уже почти
   интерфейс; оформить протокол (fetch → list[RawProduct]).
   Done: кондиционерные тесты зелёные, oasis-адаптер объявлен в профиле строкой
   `source: oasis_db`.
4. **Категорийный слой.** AirConditionerType/SubType → в профиль как generic
   `category_fields` (маппинг поле→тег). base_tags уже в конфиге.
   Done: снапшот-тест фида зелёный (XML не изменился), маппинг задаётся YAML-ом.

## Этап B — профиль «Венки» (данные уже доступны)

5. **Адаптер `ritualb2b_site`.** Тянет products.js с сайта (или по SSH из webroot),
   парсит 55 товаров → RawProduct (name, price, photo-URL, descShort/descLong, размер).
   Сначала зафиксировать РЕАЛЬНУЮ структуру products.js как фикстуру (правило: не гадать
   схемы — брать живую).
   Done: юнит-тест на фикстуре: 55 товаров, поля заполнены.
6. **Профиль `profiles/wreaths.yaml`.** Категорийные теги (из ответа владельца по
   категории), шаблон описания (descLong + постоянный хвост: доставка/контакты),
   правила цены (с сайта как есть или наценка — уточнить у владельца одним вопросом
   при первом фиде), режим карточек `ritual`.
   Done: `python -m avito_bridge --profile wreaths` собирает XML локально; валидный
   по структуре Автозагрузки; снапшот-тест кондиционеров зелёный.
7. **Группировка для венков.** Кондиционерные «серии» не нужны: один товар = одно
   объявление (тривиальный группировщик в профиле: `grouping: per_item`).
   Done: в XML 55 Ad с уникальными Id (ad_id от sku).

## Этап C — публикация и студия

8. **Второй аккаунт в клиенте.** AvitoClient уже параметризован ключами; профиль несёт
   свои ключи; деплой фида венков на nginx отдельным URL.
   Done: фид виден по https://…/wreaths.xml; Автозагрузка 2-го аккаунта видит файл
   (нужны ключи и настройка ЛК — владелец).
9. **Студия: селектор профиля.** Комбо-бокс в тулбаре; смена профиля = перечитать
   каталог выбранного профиля (catalog_export принимает --profile).
   Done: pytest-qt тест переключения; вручную: в таблице видны венки.
10. **Первая живая публикация венков.** Проверка v4 uploads отчёта 2-го аккаунта.
    Done: ≥1 объявление published — критерий успеха всего проекта.

## Параллелизуемость
- Шаги 1–4 строго последовательно (фундамент).
- Шаг 5 (адаптер) можно делать параллельно с 3–4.
- Шаги 8 и 9 независимы друг от друга.

## Не забыть
- Ветка, не main. PR в конце этапа, как с manual-price-override.
- После каждого этапа — обновить память проекта.
- «В тылышке» из голосового описания владельца интерпретировано как «шаблоны текстов
  под свой стиль» — если имелось в виду что-то ещё (Телега?), уточнить при демо этапа B.
