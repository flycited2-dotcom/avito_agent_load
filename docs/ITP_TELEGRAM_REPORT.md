# Отчёты об остатках IT-партнёра — исправление 01.10.2026

Рассылка работает на сервере `sprintbox-itp`, а не на локальном компьютере. Служба: `climat-simf-itp-crimea-report.service`, таймер: `climat-simf-itp-crimea-report.timer`. Получатель — существующий личный чат владельца; проверен через getChat. Бот: `8650114784`, `@b2b_asist_me_bot`. Секреты остаются в серверном `.env`.

До исправления отчёт запускался ежедневно в 08:00 МСК. 30 сентября и 1 октября вместо успешного завершения в журнале записано `fetch failed`; 1 октября ExecMainStatus=1. Четырёхчасовое получение остатков продолжало работать. Прямой HTTPS к api.telegram.org по IPv4 завершался connect timeout. Локальный resolver не возвращал AAAA; публичные DNS возвращали рабочий IPv6. Через этот маршрут getMe и getChat успешно прошли.

Теперь отчёт отправляется ежедневно в **09:00, 13:00 и 17:00 Europe/Moscow**. Перед отправкой запрашиваются свежие остатки. Время обновления указывается в сообщении. После перезапуска сервера таймер догоняет пропущенный запуск.

Исправления:

- `scripts/telegram-report-ipv6.cjs` подключён только к процессу отчёта через systemd drop-in. Для api.telegram.org используются AAAA, полученные через публичные DNS 1.1.1.1/8.8.8.8; остальные адреса разрешаются обычным способом. Адрес Telegram не зашит в код, сертификат TLS проверяется как обычно.
- Для ошибок установления соединения добавлены до трёх попыток. Служба повторяет неудачный запуск с интервалом 60 секунд, не более трёх запусков за 30 минут.
- Проверяются HTTP-статус, Telegram `ok` и `message_id`.
- `.runtime/itp-crimea-report-delivery.json` хранит защищённую запись о доставке. При повторе в пределах того же часа подтверждённое сообщение не отправляется снова; недоставленный CSV повторяется с тем же снимком остатков. Запись привязана к боту и получателю. Потеря ответа после фактического принятия Telegram остаётся неоднозначной — абсолютная гарантия отсутствия дублей не заявляется.
- Журнал различает этапы получения остатков, сохранения снимка и доставки Telegram; токены удаляются из сообщения об ошибке.

Проверено: три теста маршрутизации, восстановление после сбоя отправки CSV, сохранение одинакового снимка для текста/CSV, повтор завершённого отчёта и HTTP 200 с отклонением Bot API. После применения сервер отправил свежие остатки в 13:05 МСК 01.10.2026: 18 позиций, 25 единиц; подтверждены message_id 946 и 947. Служба завершилась с кодом 0.

Исходники исправления, проверок и процедура установки сохранены относительно рабочей папки Avito в `outputs/itp-report-repair-20261001/`. Изменённые файлы относятся к серверному проекту `/var/www/climat-simf.ru`; при его следующем полном развёртывании эти изменения необходимо сохранить. В устаревший локальный checkout сайта они автоматически не переносились.

Резервная копия: `/opt/avito-bridge/state/itp-report-repair-20261001T100541Z`. Журнал применения — `deployment.json`, статус committed. Расписание и настройки находятся в `/etc/systemd/system/climat-simf-itp-crimea-report.timer` и `climat-simf-itp-crimea-report.service.d/report-reliability.conf`.

Диагностика: `systemctl show climat-simf-itp-crimea-report.service`, `systemctl list-timers climat-simf-itp-crimea-report.timer`, журнал `/var/log/climat-simf.ru/itp-crimea-stock.log`. Не выводить журнал без удаления токенов, не читать секретный `.env` в чат.
