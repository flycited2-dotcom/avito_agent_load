# Инбокс — куда кидать фото и контент

Один раз кладёшь сюда фото + тексты + список «что публиковать», говоришь мне
**«обработай инбокс»** — сначала запускается локальная проверка и атомарное обновление
конфига/описаний. Публикация на сервер выполняется только отдельным явным запуском
с `--deploy`.

## Структура
```
inbox/
├── photos/            ← фото товаров. Имя файла = АРТИКУЛ (nc_code). jpg/webp/png.
│                        напр. НС-1763718.jpg   (артикул берёшь из Excel / из строки серии)
├── descriptions/      ← тексты описаний (по одному на серию). Имя — любое, напр. tessey.txt
└── inbox.yaml         ← что публикуем (заполняешь по образцу inbox.example.yaml)
```

## Как заполнять `inbox.yaml`
```yaml
items:
  # 1) Товар В НАЛИЧИИ, но без фото в БД (напр. Ballu Tessey) — даём своё фото:
  - series_key: "rusklimat|ballu|tessey dc"   # ключ серии (колонка key в Excel)
    photos: ["НС-1763718"]                     # артикулы, чьи фото лежат в photos/ (без расширения)
    description: "tessey.txt"                  # файл из descriptions/ (можно опустить — тогда автотекст)

  # 2) Товар ПОД ЗАКАЗ (нет в наличии в БД) — добавляем принудительно с ручной ценой:
  - force_nc: "НС-1690797"                     # артикул товара
    price: 18990                               # ручная цена, ₽
    series_name: "ACE-07 FH/N6"                # имя серии (чтобы было отдельным объявлением)
    photos: ["НС-1690797"]                     # если у него нет фото в БД — положи в photos/
    description: "ace07.txt"
```

## Что происходит при «обработай инбокс» (скрипт `scripts/apply_inbox.py`)
1. Все имена, цены, фото, описания и структура YAML проверяются до первой записи.
2. Каждое фото из `photos/` конвертируется в JPEG. При `--deploy` оно загружается
   через скрытый временный файл под content-addressed именем
   `/static/manual-photos/{арт}-{sha256}.jpg`. Неудачный деплой не меняет байты
   по URL, который использует прежний фид.
3. Описания, `manifest.json` и `config.yaml` обновляются одной локальной
   транзакцией. Ошибка записи или публикации возвращает все локальные файлы в
   исходное состояние.
4. Серии из `items` добавляются в `selected_series` (или `force_include`, если
   товар под заказ). Значения записываются как YAML-данные, без shell-подстановки.
5. При `--deploy` архив передаётся fail-closed publisher: тот строит кандидатный
   фид отдельно, проверяет XML и минимальное число объявлений и лишь затем
   атомарно заменяет рабочий фид. Ошибка SSH или валидации не считается успехом.

Скрипт намеренно не запускает генерацию новых карточек автоматически. Если новой
серии нужна уникальная карточка, сначала выполните и проверьте штатный
`avito_bridge.cards_run`, затем повторите безопасную публикацию.

## Запуск

```powershell
python -m pip install -e ".[dev]"

# Проверить входные данные и применить локальные изменения; сети и SSH нет
python scripts/apply_inbox.py

# После просмотра git diff — загрузить фото и безопасно опубликовать кандидат
$env:AVITO_BRIDGE_SSH_HOST = "deploy@example.test"
$env:AVITO_BRIDGE_SSH_KEY = "C:\Users\me\.ssh\deploy-key"
python scripts/apply_inbox.py --deploy
```

Адрес production и приватный ключ намеренно не зашиты в репозиторий. Значения
двух переменных берутся из приватного операционного runbook.

## Коротко
- **Просто фото добавить** товару без картинки → положи `photos/{артикул}.jpg` + строку в `inbox.yaml`.
- **Текст описания** → `descriptions/{имя}.txt` + `description: имя.txt` в item.
- **Опубликовать серию** → укажи `series_key` (или `force_nc`+`price` под заказ).
- Артикулы (nc_code) и ключи серий берёшь из актуального экспортированного
  каталога; исходные файлы поставщиков в Git не добавляются.
